### 2. `presidio_analyzer/pattern.py` — the atom (66 lines)
**Say:** "This is the smallest unit of the whole system: a name, a regex, and
a confidence score between 0 and 1. Every detection in this project bottoms
out here."

```python
Pattern("All Credit Cards (weak)", r"\b(?!1\d{12}...)...", 0.3)
```

Note the score is **0.3** — "weak." The regex alone is not trusted.

---

### 3. `presidio_analyzer/pattern_recognizer.py` — the detection engine
**Say:** "This runs every pattern over the text. The important part is what
happens *after* a regex match."

Point at `__analyze_patterns()`, around the `validate_result` call:
- regex matches → tentative score (e.g. 0.3)
- subclass runs `validate_result()` (a checksum)
- **checksum passes → score jumps to 1.0**
- **checksum fails → score drops to 0 and the match is discarded**

**This is the key mechanism of the entire project.** The regex finds
*candidates*; the checksum decides *truth*.

### 5. `regex_engine.py` — what we wrote ourselves

## PART 4 — What works, and why

**The rule: regex works on identifiers that a human being designed to a
specification.**

| Type | Result | Why it works |
|---|---|---|
| EMAIL_ADDRESS | P 1.00 / R 1.00 | RFC-defined grammar; the whole format is expressible as a rule |
| IP_ADDRESS | P 1.00 / R 1.00 | Fixed numeric structure, validated by Python's `ipaddress` module |
| IBAN_CODE | P 1.00 / R 0.95 | mod-97 checksum — arithmetic either passes or it doesn't |
| CREDIT_CARD | P 1.00 / R 0.77 | Luhn checksum, same reason |
| CRYPTO | (no labels in dataset) | Base58 / Bech32 checksums |

**Why precision is 1.00 across all of these:** a random string essentially
never passes a checksum by accident. The checksum eliminates false positives
almost entirely — that is the single most important finding.

## PART 5 — What doesn't work, and why

### 5.1 Names, addresses, organizations — 2,337 spans, 0% detected
`PERSON`, `STREET_ADDRESS`, `GPE`, `ORGANIZATION`, `TITLE`, `AGE`, `NRP`.

**Say:** "A regex matches *character shape*. Recognizing a name requires
*meaning*. 'John Smith' and 'Red Rock' are structurally identical — two
capitalized words. Nothing in the characters distinguishes a person from a
place. You cannot write a rule for this; you need a model that has learned
what names look like in context."

**This is a hard boundary, not an implementation gap.**

### 5.2 Dates — 40% recall
Partially formal. `2024-03-15` is a *format*; "March 15th" is *language*.
Regex gets the formal half and nothing else. The 13 date patterns in
`date_recognizer.py` cover numeric layouts only.

### 5.3 Phone numbers — the only type with false positives (20)
Semi-formal: the format varies by country, and digit strings are overloaded —
an order number and a phone number can look identical. `phonenumbers` scans
8 regions at leniency 1 and sometimes matches numbers that aren't phones.
**Ambiguity is what breaks regex**, and phone numbers are the ambiguous case.

### 5.4 The 31 "failed" credit cards — a failure that is actually correct
The diagnosis in `FULL_TEST_REPORT.txt` Part 2A shows many of these card
numbers **fail the Luhn checksum in the test data itself**. Our recognizer
saw a card-shaped string, ran the checksum, and correctly refused to validate
an invalid number.

**Say:** "Counted as a miss against ground truth, but the code did the right
thing. If I'd accepted them, precision would have dropped. This is a case
where the benchmark and correct behaviour disagree."

Strong point — shows you read the failures instead of reporting the number.

## PART 6 — The deeper finding (close with this)

**1. Coverage is limited by what we vendored.**
Presidio has ~87 regex recognizers: 10 generic (we implemented all 10) and
~77 country-specific (we implemented none). For this dataset only two would
have mattered — `US_SSN` (16 spans) and `US_DRIVER_LICENSE` (5 spans).

**2. Some of Presidio's "regex" recognizers are not actually standalone.**
`us_ssn_recognizer.py` scores its patterns at **0.05**, and
`us_driver_license_recognizer.py` at **0.01** — that one matches *any* 6-to-14
digit number. They are only usable because Presidio's `ContextAwareEnhancer`
raises the score when words like "ssn" or "social security" appear nearby.
**That enhancer needs lemmatized tokens from an NLP engine**, which a
zero-dependency build doesn't have.

**So "regex-only" has a ceiling even inside Presidio's own regex recognizers.**
The genuinely self-sufficient ones are exactly the checksum-backed types —
which is why those are the ones scoring 1.00 precision.

**3. The architectural conclusion.**
- Checksummable identifiers → regex, ~1.00 precision, no model, runs anywhere
- Free-text entities → require NER, which means model weights and compute
- Production systems are therefore **hybrid**: regex for structured PII,
  NER for the rest
- The regex tier is the one that ships to edge devices: 3 pip packages,
  no weights, deterministic, same output every run

## Likely questions, and answers

**"Did you train anything?"**
No. There is no model and no training phase. The rules were hand-written by
Presidio's developers from published specifications (card prefixes, Luhn,
mod-97, RFC 4122). The 1,500-record dataset is used only to *measure*, never
to fit — deleting it would not change a single detection.

**"Why is recall only 67%?"**
Because 33% of reachable spans are in formats no rule covers — mostly
spelled-out dates — plus credit cards whose test values fail their own
checksum. Precision stays at 0.94 because checksums prevent false positives.

**"Why not just add NER?"**
That's the correct production answer, and it's the tradeoff being measured
here: NER would lift recall on the 85% we can't touch, at the cost of model
weights (13 MB–1 GB), inference latency, and a training/evaluation pipeline.
For an edge device, the regex tier may be the only affordable option.

**"Is this Microsoft's code or yours?"**
24 files are Microsoft's, copied with source URLs in the headers. Two have a
one-line documented modification. `regex_engine.py` and the test harnesses
are mine, because Presidio's own engines can't run without spaCy.
